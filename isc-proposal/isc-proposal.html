An rdlocal companion package with a Weblate bridge

Executive Summary

rdlocal (formerly rhelpi18n, ISC grant 2023-2) lets R users read package help pages in their own language by installing a translation module. After Google Summer of Code 2026 it handles dynamic content and package updates, and it was user-tested at the R Project Sprint 2026. The remaining bottleneck is producing translations: every string is written by hand in YAML files, and the help for base alone is about 1.1 million characters.

I propose babelrd, a companion package that fills a translation module with a machine-translated first draft using the user’s own DeepL, Microsoft, Google or LLM key. It protects Rd markup and rdlocal placeholders, and it checks that every page still parses and renders. Every drafted string is marked fuzzy so readers and reviewers know it is unreviewed. A two-way bridge between modules and gettext PO files lets translation teams review drafts in Weblate, the platform R already uses for its messages. The output is one shared, reviewable module per package and language, not a private translation that each user pays for again.

The request is $5,600 (140 hours at $40/h) over about seven months, in four milestones ordered so that partial funding still delivers a working draft → review loop.

The Problem

rdlocal works; producing translations doesn’t scale

rdlocal lets a package’s help be read in another language without changing the package. A translation module holds one YAML file per help page, and each string’s original sits next to its translation. When a user opens a help page in their language, rdlocal swaps in the translated strings. Since GSoC 2026 it also keeps translations valid when a package is reinstalled or updated: dynamic values become {ISEXPR_n} placeholders, and changed strings are flagged fuzzy instead of being silently dropped.

Every translation is still typed by hand. Approximate sizes of the translatable text (titles, descriptions, arguments, details, value), measured with tools::Rd_db():

Package Help topics Characters
base 446 1,142,000
stats 313 688,000
utils 160 425,000
survival 133 282,000
MASS 155 119,000

base alone is roughly 190,000 words. At a professional translator’s pace, that is months of work per language, and it has to be kept up to date. After creating a module during Sprint 2026 user testing, Paola Corrales wrote: “Having translated only one yaml, I think it would be great to provide a way to get a machine translation as a starting point” (sprint #10).

Why “just run it through a translator” breaks help pages

Help strings are not plain prose. This is part of mean()’s x argument as it appears in a module:

An \R{} object. Currently there are methods for numeric/logical vectors
and \link[=Dates]{date}, \link{date-time} and \link{time interval} objects.
Complex vectors are allowed for \code{trim = 0}, only.

A correct translation must:

  • translate the link text (date) but keep the link target (=Dates);
  • leave \code{trim = 0} and \R{} untouched;
  • keep every {ISEXPR_n} placeholder exactly once.

Generic machine translation gets these wrong. When it does, rdlocal can’t match or re-parse the page, and the user silently sees English or a broken page. Without guarding and checking, machine output creates more review work than it saves.

The second gap is review. R’s message translations are reviewed on the R project’s Weblate instance, where bulk machine translation is added as “needs editing” for a human to check (r-dev-day #66). rdlocal modules are YAML inside R packages, and there is no path between them and Weblate or any other gettext tool. That task is open as sprint #17.

Existing work

Tool What it does What it doesn’t do
lang (Posit) Translates help live with an LLM, per user and per session Translations aren’t shared, reviewed or kept; every user pays again; no rdlocal placeholders
babeldown (rOpenSci, ISC 2022-2) DeepL translation of Markdown/Quarto with glossaries Doesn’t handle Rd markup or rdlocal modules. babelrd follows its approach for Rd.
deeplr DeepL API wrapper No knowledge of Rd or modules
R’s Weblate Reviewed translation of R’s messages (PO files) No help pages

What solving it enables

  • A translation team can start a new package and language from a complete, render-checked draft instead of an empty file.
  • Translators can review in Weblate, with its memory, glossary and review workflow, instead of editing YAML.
  • Reviewed translations can later be offered for base and recommended packages.

This builds on three earlier ISC investments:

  • rhelpi18n/rdlocal (2023-2)
  • babeldown (2022-2)
  • the Consistent Translations Glossary (2025-2), which babelrd uses to keep terms consistent

It also delivers two items on the Multilingual Documentation Working Group’s plan: “keep translations up-to-date” and “transform between formats accepted by existing translation services”.

No changes to R itself are proposed.

The proposal

Overview

babelrd is a separate package. rdlocal stays free of API keys and network calls, as agreed in sprint #10. babelrd works on the module files that rdlocal::i18n_module_create() already produces:

package help ─ i18n_module_create() ─► module (YAML, empty translations)
                                            │
  babelrd::draft()    DeepL / Microsoft / Google / LLM (user's own key)
                      markup + placeholders protected, glossary applied,
                      every string written as fuzzy + provenance
                                            │
  babelrd::check()    re-parse, placeholder count, render, glossary
                                            │
  review in YAML  ◄─────────────────────────┴──► babelrd::to_po() / from_po()
                                                  Weblate or any PO editor
                                            │
  publish: the module is installed and served by rdlocal as today

Sketch of the intended API:

rdlocal::i18n_module_create("MASS.es", language = "es",
                            module_path = "MASS.es", package_path = "MASS")
babelrd::estimate("MASS.es")                     # characters, cost vs free tiers
babelrd::draft("MASS.es", provider = "deepl")    # key from DEEPL_API_KEY
babelrd::check("MASS.es")                        # per-page report
babelrd::to_po("MASS.es", "MASS-es.po")          # upload to Weblate
babelrd::from_po("MASS.es", "MASS-es.po")        # reviewed strings back in

Detail

Minimum Viable Product

draft() and check() with one provider (DeepL). They take an empty rdlocal module and produce a fully drafted module. Every page must pass the checks, and every drafted string is flagged fuzzy, so rdlocal already shows it with a note that the text is unreviewed. draft() only fills empty translations; it never overwrites human work.

Architecture

  1. Protect. Each string is parsed into prose and protected spans:
    • \code{}, \link targets, \eqn, {ISEXPR_n}, user macros and similar become opaque tokens;
    • link text and \emph{} stay translatable.
    For DeepL and Microsoft the tokens are sent as XML/HTML tags marked “do not translate”. For LLMs, ellmer with structured output is used, which also allows local models via Ollama.
  2. Translate in batches per help page, so terms stay consistent within a page. Glossary terms from r-devel/glossary are passed as a DeepL glossary or as prompt constraints.
  3. Restore and check.
    • Each placeholder must appear exactly once.
    • The string must re-parse as Rd.
    • The page must render with tools::Rd2txt().
    • Glossary terms must be used.
    Strings that fail are left empty (never broken) and listed in the report.
  4. Record provenance. Each drafted string gets fuzzy: yes and machine: <provider> <date> (additive YAML fields).
  5. PO bridge.
    • One PO entry per string, with msgctxt = topic + section + argument, so entries map back to YAML.
    • fuzzy ⇄ gettext #, fuzzy (Weblate’s “needs editing”).
    • Placeholders are declared with Weblate’s placeholders: check flag, so translators can’t drop them.
    • from_po() writes only strings whose msgid still equals the module’s original. Anything else is reported, so a stale PO can never overwrite newer text.

Assumptions

  • Module schema: the YAML schema in rdlocal stays stable, or changes additively. I work with its maintainer, and I wrote the current version.
  • Machine translation quality: drafts are good enough that reviewing is faster than translating. Bulk machine translation tried on R’s Weblate let a translator progress faster, but drafts “sometimes got the meaning completely wrong” (r-dev-day #66). For that reason nothing is ever marked reviewed automatically. Milestone 4 measures the edit rate.
  • CRAN: rdlocal is on r-universe only (it patches utils:::.getHelpFile). babelrd will also be distributed through r-universe. It uses rdlocal only for module I/O, so it can move to CRAN together with rdlocal.

External dependencies

  • rdlocal
  • yaml
  • httr2 (DeepL, Microsoft and Google APIs)
  • ellmer (LLMs, optional)
  • r-devel/glossary data (optional)
  • a PO parser: written in-package, since the format needed is small
  • users’ own API keys: nothing is hosted or paid for by the project

Weblate hosting of help-page components is not required for any deliverable. The PO files work with any gettext tool, such as Poedit.

Failure modes and recovery

Risk Recovery
A provider mangles tokens Per-string retry with a stricter mode. If it still fails, leave the string empty and report it. The page falls back to English, as rdlocal already does.
Output quality is poor for a language Drafts stay fuzzy. The M4 edit-rate data is published, so teams can choose their provider.
A provider changes its API or terms Backends sit behind a single small function each. There are at least two MT backends plus LLMs.
Weblate admins don’t want help-page components yet PO round-trip still works locally. Hosting becomes future work.

Success

Definition of done

  • babelrd is available from r-universe, and R CMD check passes on Linux, macOS and Windows.
  • For the test modules, every drafted page passes check(): placeholders intact, the page re-parses and renders.
  • A module goes YAML → PO → YAML with no change except the reviewed strings. This is covered by tests.
  • A full Spanish draft of one recommended package has been published as an rdlocal module, with a public review report.
  • There are two vignettes (translators; translation teams / Weblate) and the R Consortium blog posts.

Measuring success

  • During the project: milestone dates are met, and CI stays green.
  • Draft quality: the share of strings that pass check() on the first try (target: over 95%).
  • Pilot: the edit rate from community review, published per provider, which tells teams whether drafts actually save time.
  • Adoption, within 6 months of the end:
    • new translation modules started with babelrd;
    • at least one translation team using the PO route;
    • issues and PRs from people other than me.

Future work

  • Hosting help-page components for base and recommended packages on R’s Weblate, if the admins and language teams want it.
  • Drafting translations of vignettes by combining babelrd with babeldown (rdlocal issue #5).
  • A hook in R’s help system so that rdlocal, and therefore babelrd modules, can go to CRAN (sprint #16).
